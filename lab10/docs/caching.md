# Описание механизма кеширования

## Алгоритм Cache-Aside
В системе реализован алгоритм «кеш сбоку» для эндпоинта `GET /api/bookings`.

1. **Проверка кеша**: При запросе система ищет данные по ключу `bookings:all`.
2. **Промах (MISS)**: Если данных нет, выполняется SQL-запрос к PostgreSQL через `BookingRepository`.
3. **Запись в кеш**: Полученный массив сохраняется в кеш с TTL (время жизни) 60 секунд.
4. **Попадание (HIT)**: Повторный запрос берет данные из кеша, минуя базу данных.

## Ключи и TTL
- Ключ: `bookings:all` (так как возвращается список всех записей).
- TTL: 60 секунд. Это защита от «залипания» данных, если запись в кеш не была сброшена вручную.

## Инвалидация
При добавлении, изменении или удалении бронирования кеш должен сбрасываться. В рамках учебной реализации мы полагаемся на TTL (естественное истечение срока), но в реальном проекте мы бы добавили вызов `Cache::delete('bookings:all')` в методы `store`, `update` и `destroy` контроллера.
